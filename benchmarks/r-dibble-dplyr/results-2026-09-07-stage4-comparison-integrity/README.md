# Stage 4 comparison input bindings

This additive audit addresses [PR199's comparison-binding finding](https://github.com/jbearak/dta-parser/pull/199#discussion_r3949564866). The [executed historical summarizer](https://github.com/jbearak/dta-parser/blob/f28c5fd481ad15586e013066e385cbf363354526/benchmarks/r-dibble-dplyr/results-2026-09-07-stage4-review-fix/benchmark/source/summarize-c8ca0a4-performance.py) checked derived output hashes without checking their recorded baseline/candidate manifest hashes or comparator identity. Its exact old validation loop admits stale identity fields when the output files and their hashes remain internally consistent. That is a checker gap; the actual archived identities all match.

The new [auditor](audit-comparison-bindings.py) checks all six current archived manifest hashes, the three qualified comparator hashes and their actual source bytes **before reading any comparison result**. It also checks the heap metric-verifier hash against the qualification and both heap manifests, fixed recorded paths/source labels/commands, exact comparison output file sets, all seven result-file hashes, and input stability through completion. Original absolute paths are retained as identity labels; reads use only contained files in the supplied archive. A new receipt must be outside the immutable archive and must not already exist.

The [fresh actual receipt](actual-audit.json) binds 20 consumed inputs. It confirms 206 atomic comparison rows with 15 flags, 46 double rows with no flags, 30 atomic/six double memory rows and 36 heap rows. The six manifest and three comparator identities match the completed [paired qualification](https://github.com/jbearak/dta-parser/blob/f28c5fd481ad15586e013066e385cbf363354526/benchmarks/r-dibble-dplyr/results-2026-09-07-stage4-review-fix/benchmark/qualification.json). This is a new identity check of the same frozen data, not a new benchmark or an independent reimplementation of every comparator formula. It does not establish that the older checker already enforced these predicates.

The [guard driver](test-comparison-bindings.py) uses small synthetic records. Its [87-case result](guards/summary.json) covers 29 cases each with default Python, `-O`, and environment-only `PYTHONOPTIMIZE=1`. Each mode includes one valid fixture and 28 expected rejections, exact rejection diagnostics, unchanged input bytes, and preserved/absent output on rejection. In each mode, the exact extracted historical result-only loop accepts all nine stale manifest/comparator-field cases; the new auditor rejects them. Changed comparator bytes, recorded paths, heap verifier/runner identities, derived output bytes, missing qualified identity, wrong comparator command and unsafe/existing output paths are also covered. No archived script's full workload executes during these tests.

Run the portable verifier from a checkout containing the preceding evidence partition:

```sh
python3 benchmarks/r-dibble-dplyr/results-2026-09-07-stage4-comparison-integrity/verify.py
```

`--archive /path/to/results-2026-09-07-stage4-review-fix` selects another unchanged archive copy. The verifier checks the exact supplement inventory, bytes/executable bits, current guard source identities and distinct launch modes, then reruns only the read-only identity auditor and compares its result with the saved receipt. To create a separate audit receipt, run `python3 audit-comparison-bindings.py ARCHIVE NEW_OUTPUT.json`. To repeat the tiny guard suite, run `python3 test-comparison-bindings.py AUDITOR HISTORICAL_SUMMARIZER NEW_OUTPUT_DIRECTORY`. The index deliberately excludes itself; review and commit receipts bind its completed bytes.

All original A/B records, the old summarizer, qualification/progress commands, indexes and dated report remain unchanged. The new helper has conventional docstrings for its current interfaces; no historical script is rewritten to change a documentation metric. Exact command records retain their original local path labels under the established execution-evidence policy. No R, package build, comparator rerun, benchmark, fertility or renv operation was required. The same 12 base-R read/coercion costs and three delegated-filter flags remain visible, with the filters required in Stage 6. Overall performance acceptance, Stages 5–9 and the final actual fertility renv install/test/restore remain open.
