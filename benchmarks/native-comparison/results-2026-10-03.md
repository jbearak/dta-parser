# Native comparison follow-up, 2026-10-03

The accepted float-pair kernel `e265f737` uses **0.45 to 0.55× typed-double CPU**
on the million-row ordinary/sparse-missing matrix. It takes 0.169 to 0.227 ms per
public comparison, including result allocation and automatic collection.
Against the preceding exact float loop, it improves CPU by 2.02 to 2.78×.
Missing-free pairs use 0.237 to 0.249× bare-double CPU. These results establish
parity for this matrix, not for all compact operations or input layouts.

The dense guard is measured separately against that same exact float loop.
Random-half and all-tagged inputs range from 0.7% less to 2.35% more CPU;
paired-round speedup medians are 0.984 to 0.990×. Clustered-half inputs use
30 to 32% less CPU, a 1.43 to 1.48× speedup. The small remaining proof cost is
explicitly accepted in return for the measured ordinary/sparse gains.

Decoded-double pairs improve 4.06 to 5.82× CPU in the original ordinary/sparse
matrix and 1.56 to 2.67× in a separate dense matrix. Random missing doubles remain
much slower than compact floats. This PR does not claim that residual is fixed.

## Final kernel and its limits

Storage, operator and Stata release are selected outside the row loop.
A 64-row block is ordinary only when the unsigned maximum of the operands'
absolute float bit patterns is below the first missing encoding. This proves
both operands finite and observed. Such blocks use direct vector comparisons.
Other blocks use the exact vectorizable missing-rank loop.

After four consecutive failed block proofs, the kernel uses the exact loop
for the rest of the captured span. This selects an algorithm; it assumes
nothing about later values. An ordinary block resets the counter, and each
new span starts fresh. Validity accumulation does not short-circuit, so an
unsupported NaN before or after the switch still declines the whole native
call. No cached column-domain fact or ownership change is introduced.

A raw threshold is insufficient for every accepted import. Modern imports
recognize precisely 27 missing codes and can contain observed values between
those codes, high finite values or infinity. Legacy releases retain their
broader classification. Large negative values and infinities conservatively
use the exact path. Signed zeros retain IEEE comparison behavior. Scalar
float comparisons still widen exactly to binary64, preserving the full R
scalar precision. Temporal and mixed-storage cases keep their existing paths.

The decoded-double pair loop compares ordinary doubles directly and examines
NaN payloads only when an operand is NaN. Supported payloads use Stata missing
order; unsupported payloads retain the existing fallback. This removes the
previous value-and-rank reconstruction at each row. Dense random missing
inputs still expose the cost of the per-row NaN branch.

## Measured stages

Each row describes its own paired experiment. Speedups from different rows
must not be multiplied into an end-to-end claim. Five ordinary/sparse
experiments contain 432 observations each; four dense screens contain 144 each.
All source revisions, raw observations, controls and rejected results remain
available.

| Experiment | Before → after | Result |
| --- | --- | --- |
| Double pair and retained scheduling | `c17ef21e` → `6f95ab2c` | Typed-double pairs 4.06 to 5.82× faster CPU in the ordinary/sparse matrix |
| Direct float comparison with exact missing ranks | `6f95ab2c` → `e36e50c2` | Float pairs 1.35 to 1.42× faster CPU, reaching 1.07 to 1.24× typed-double CPU |
| Rejected per-row threshold | `e36e50c2` → `c21a79b3` | Ordinary/sparse pairs 1.08 to 1.21× faster, dense inputs 1.72 to 5.45× slower |
| Block proof without a stop rule | `e36e50c2` → `deaa84e7` | Ordinary/sparse pairs 2.17 to 2.67× faster, random/all-tagged dense inputs 12 to 15% more CPU |

## Why the rejected shortcut mattered

A per-row threshold branch looked faster on ordinary and sparse inputs but
prevented vectorization on this arm64 build. The dense screen showed the cost:

| Missing layout | Exact float CPU ms | Per-row threshold CPU ms | Threshold / exact CPU |
| --- | ---: | ---: | ---: |
| Independently randomized half of each input | 0.465 to 0.466 | 2.534 to 2.538 | 5.44 to 5.45× |
| First half of both inputs | 0.455 | 0.783 | 1.72× |
| All rows tagged | 0.454 | 1.188 to 1.190 | 2.62× |

The random layout has at least one missing operand in 749,863 rows; the
clustered layout has 500,000. These layouts do not isolate branch prediction
alone. Comparing with the much slower dense typed-double control would hide
the compact-float regression. The [rejected observations](results-2026-10-03/dense-threshold/density-paired-v1/raw.csv)
and [independent audit](results-2026-10-03/dense-threshold/independent-audit.json)
are retained.

The first block version removed that scalar branch, but checking every block
still wasted work on dense inputs. Its [ordinary/sparse](results-2026-10-03/final-stages/float-block-max-paired/summary.csv)
and [dense](results-2026-10-03/final-stages/density-max-paired-v1/summary.csv)
results are also retained. The accepted stop rule bounds those optional scans.
Generated code uses SIMD unsigned maxima and vector comparisons; this is
compiler evidence, not a separate performance claim.

## Scheduling trades CPU for elapsed time

Retained float regions now use the same serial policy as plain compact floats
and existing scalar fast paths, including positive requested thread counts.
The region walker still handles unequal chunk boundaries.

The first experiment isolates this scheduling change before the float-loop
improvements. Automatic retained-float CPU improves 1.28 to 1.45×, while elapsed
time becomes 2.05 to 2.64× longer. Single-thread results remain approximately
unchanged. The subsequent loop changes improve both CPU and elapsed time
against the serial version. No combined elapsed-time claim is calculated
from separate experiments, and no universal worker policy is inferred.

## Protocol and source binding

Ordinary/sparse experiments use six balanced rounds, fresh R processes for
each build/round and all six representation orders. Each build has 36 cases:
pair `<` and `==`, scalar `< 1.01`, threads 1 and automatic, and zero or sparse
occurrences of all 27 missing codes. Inputs have one million rows. Retained
X spans contain 8,191 values and Y spans 16,385, exercising unequal boundaries.
Dense screens use six balanced rounds, both pair operators, compact and typed
doubles, and random-half, clustered-half and all-tagged layouts.

Complete results, decoded input bytes, independent integer-rank oracles,
metadata, native eligibility and representation state are checked outside
timing. Construction, explicit collection, calibration and verification are
excluded; result allocation and automatic collection are included. Calibration
targets 300 ms CPU. Local builds, tests and other benchmarks are stopped during
measurement. The host is arm64 macOS with R 4.6.1, without hardware isolation
from normal desktop activity. These warm-operation results do not establish
reader throughput, memory savings, confidence intervals or arbitrary chunk
and missing distributions.

Each controller verifies recorded package sources, installed libraries,
actual Rscript/runtime and controller files before and after workers. The
first baseline's package inventory matches merged main `460db463`. Final
measured source `e265f737` includes grouping main `6e00be97`. Its clean build,
source patch and complete receipts are published. The final controller also
gets its descriptive R version from the exact worker launcher. Earlier
controllers bound that launcher/runtime correctly but obtained descriptive
version text through PATH; their original records are not rewritten. The
maintained benchmark explicitly requires the Unix R executable layout.
