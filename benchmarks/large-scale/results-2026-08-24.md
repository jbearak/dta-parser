# Rust 1.98 and lazy-string load results (2026-08-24)

Environment: Apple M4 Max, 128 GB RAM, macOS 26.5.2, R 4.6.1. The baseline
package used Homebrew rustc 1.97.1. The optimized package used Homebrew rustc
1.98.0 and the R bridge's standard optimized release profile.
Both runs used the same deterministic, warm-cache 40-column Stata 15 files on
the same host. Direct-R/Rust-vector exact identity and sampled haven parity
passed before timing.

The baseline was captured before edits with three measured iterations. The
optimized result used seven measured iterations, alternating implementation
order and running garbage collection outside the timed regions. These are
report-only measurements, not CI thresholds.

| Input | Workload | Baseline Direct-R median | Optimized Direct-R median | Load-time reduction | Optimized p05--p95 |
| --- | --- | ---: | ---: | ---: | ---: |
| 100 MB | Full, 40 columns | 0.307 s | 0.091 s | 70.4% | 0.090--0.094 s |
| 100 MB | Projected, 8 columns | 0.086 s | 0.034 s | 60.5% | 0.033--0.034 s |
| 1 GB | Full, 40 columns | 2.354 s | 0.905 s | 61.6% | 0.895--0.918 s |
| 1 GB | Projected, 8 columns | 0.821 s | 0.326 s | 60.3% | 0.324--0.331 s |

The optimized 1 GB full-load median was 1.105 GB/s. In the same final run, the
Rust-vector and haven medians were 2.526 s and 11.801 s, respectively. For the
1 GB projected workload they were 0.798 s and 3.203 s.

## Peak memory

Fresh processes loaded the 1 GB dataset and retained the returned 2,227,111 ×
40 tibble. Baseline memory is one pre-edit run; optimized memory is the median
of three runs.

| Measurement | Baseline | Optimized | Reduction |
| --- | ---: | ---: | ---: |
| Maximum RSS | 2.184 GB | 1.303 GB | 40.3% |
| Peak footprint | 2.099 GB | 1.287 GB | 38.7% |

Character columns now own compact normalized UTF-8 byte buffers and expose them
as ordinary R character vectors through ALTREP. This makes the result independent
of the input file while deferring CHARSXP creation until values are accessed.
The timed load checks dimensions but does not force every lazy character
column. Correctness validation before timing does compare all values exactly.

As a deliberately adverse comparison, calling `object.size()` immediately
after the 1 GB load forced every character column. That run peaked at 1.605 GB
RSS and a 1.589 GB footprint, still 26.5% and 24.3% below the eager baseline,
but took 5.33 s including load and full materialization. Workloads that consume
every string pay this deferred cost; workflows that select columns or inspect a
subset avoid it.
