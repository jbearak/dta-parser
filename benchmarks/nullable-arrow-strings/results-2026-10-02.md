# Nullable Arrow string construction, October 2, 2026

Moving nullable string construction into one caught C call improves nullable read CPU
by 1.084 to 1.417 times and read-plus-full-consumption CPU by 1.080 to 1.315
times in this 504-observation comparison. The largest gain is for repeated
strings. Ordinary R string allocation and interning still account for much
of the high-cardinality cost.

One null currently changes the representation of an entire Arrow string
column. A column without nulls uses a native dictionary with deferred R
strings. A nullable column becomes an ordinary R character vector during
the read. The old nullable path established a separate `R_ToplevelExec`
error context for every non-null value. The change retains the eager nullable
representation and creates all its strings within one caught C call per
column. This removes repeated error-context setup and Rust/C crossings;
it does not remove R string allocation or evaluate R expressions differently.

The [complete raw observations](results-2026-10-02/timings/raw.csv),
[summary](results-2026-10-02/timings/summary.csv),
[completion record](results-2026-10-02/timings/completion.json), and

## Results

The following are medians of six fresh-process observations, in milliseconds.
Read and full-workflow columns come from separate processes. Speedup is the
baseline median divided by the candidate median. Each file has 250,000 rows
and four columns, or one million cells.

| One thread, CPU | Read before | Read after | Read speedup | Read + full before | Read + full after | Full speedup |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Repeated strings, zero nulls | 19 | 18 | 1.06 | 35 | 35.5 | 0.99 |
| Repeated strings, one null/column | 42 | 30 | 1.40 | 48.5 | 37 | 1.31 |
| Repeated strings, 251 nulls/column | 42.5 | 30 | 1.42 | 48 | 36.5 | 1.32 |
| Nearly unique strings, zero nulls | 53 | 54.5 | 0.97 | 188 | 187 | 1.01 |
| Nearly unique strings, one null/column | 154.5 | 142 | 1.09 | 162 | 150 | 1.08 |
| Nearly unique strings, 251 nulls/column | 155 | 142 | 1.09 | 163 | 149 | 1.09 |

Automatic threading speeds the native reader stages while R string creation
remains on the R thread. It therefore changes CPU and elapsed time differently.

| Automatic threads | Read CPU before → after | Read wall before → after | Read + full CPU before → after | Read + full wall before → after |
| --- | ---: | ---: | ---: | ---: |
| Repeated, zero nulls | 26 → 26.5 | 6 → 5 | 43.5 → 43.5 | 23 → 23 |
| Repeated, one null/column | 49 → 37 | 33 → 21 | 55 → 43.5 | 39 → 27.5 |
| Repeated, 251 nulls/column | 48.5 → 37.5 | 33 → 21 | 55.5 → 44 | 39 → 28 |
| Nearly unique, zero nulls | 80 → 80 | 19 → 19.5 | 214.5 → 215 | 154 → 154 |
| Nearly unique, one null/column | 162 → 148 | 146 → 132 | 170.5 → 156.5 | 153 → 140 |
| Nearly unique, 251 nulls/column | 162 → 149 | 146 → 132 | 170 → 156 | 153.5 → 140 |

The nullable read saves about 12 to 14 ms of CPU per million cells in these
fixtures. High-cardinality nullable reads still spend about 55 ms in automatic
GC in both builds. This experiment changes the error boundary and call
placement together, so it does not assign separate savings to each mechanism.

Read-return time alone overstates the nullable penalty. In the one-thread
baseline, the nearly unique nullable file already took less total CPU to read
and fully consume than the zero-null file, 162 versus 188 ms. The candidate
reduces that to 150 ms. The dictionary route pays for native dictionary
construction and later R string creation. It caches each created R string by
dictionary ID, so later access does not repeatedly intern the same entry.
After both full traversals the zero-null result still has four dictionary
columns; nullable results have none. A full traversal here is not a forced
whole-column materialization.

The common finite-double control is unchanged at 4 ms read CPU with one
thread and 7 ms with automatic threading in read-only mode. Other finite
control cells differ by one millisecond, including an apparent 1.33 ratio
from 4 versus 3 ms. Those short observations do not establish a reader gain.

## Contract and implementation

The new [Rust chunk views](../../r-package/dtatools/src/rust/src/arrow_ffi.rs)
borrow validated Arrow offsets, values, and validity bits. The original Arrow
owners remain alive through output allocation and the complete caught call.
The [C loop](../../r-package/dtatools/src/r-bridge.c) immediately installs each
created `CHARSXP` into the preserved ordinary `STRSXP`. R allocation and
interrupt frames stay in C, so an R long jump cannot skip Rust cleanup.
The loop checks interrupts every 16,384 rows.

The change preserves NA versus empty strings, UTF-8 encoding, metadata, and
the existing embedded-NUL and excessive-string-length errors. It handles
sliced 32-bit and 64-bit offset arrays and non-byte-aligned validity slices.
Nullable values are not added to the existing dictionary ALTREP, whose
consumers currently assume no R missing strings.

## Reproduction and source binding

The [controller](run.py), [worker](worker.R), and [fixture generator](prepare.R)
implement the [recorded protocol](results-2026-10-02/timings/protocol.json).
The [README](README.md) gives the commands. Every worker starts a fresh R
process and makes one public `read_arrow()` call. Package loading, explicit
preceding GC, fixture creation, and result validation are outside timing.
Automatic GC is included. Expected strings are loaded only after all timed
access, including the second full traversal.

The 42 cases cover two thread settings, three independent workflows, six
string fixtures, and one shared finite-double control. Workflows measure read
return, read plus the first scalar of each column, and read plus complete
byte-length and missingness traversal. The last also records a separate
second traversal. Six rounds cover every permutation of zero/one/sparse null
order, rotate workflow order, alternate thread/cardinality order, and alternate
which build runs first in each pair.

Repeated-string fixtures draw from 32 generated UTF-8 strings plus common
empty-string positions. High-cardinality fixtures are nearly unique, with
the same empty positions. All potential null positions contain empty strings
in the zero-null fixture. This keeps payload bytes and offsets identical
across each null-density comparison. One and 251 nulls per column correspond
to 0.0004% and 0.1004%. Files are uncompressed and checksummed, use the standard
65,536-row batch geometry, and are read with `verify = TRUE`.

The measured baseline is clean commit
`ab64f0e4982e0cef0e6b2e1bbda1aa08f11ada74`, which includes the native
collection-pressure fix later merged in `895dd204`. This avoids attributing
that separate GC repair to nullable strings. The measured candidate is clean
commit `20a0daa1c492258017b970b551b78cce46db5637`, whose production source is
identical to `e77ade827e9659835b6da711e9c4f20155b8694d`.
Later changes only harden tests and add the benchmark.
The [package patch](results-2026-10-02/validation/measured-package.patch),
[build receipts](results-2026-10-02/builds/candidate/build-receipt.json),
and [source record](results-2026-10-02/validation/source-binding.json) bind
those facts. Measurements use R 4.6.1 on arm64 macOS. The controller uses the
same absolute Rscript launcher whose runtime hash matches both builds.

All 504 observations passed full values, missing and empty positions, original
public encoding flags, metadata, and consumption checks. Stable hashes agree
across builds, modes, thread settings, and rounds. Both clean libraries,
fixtures, runtime, and controllers have matching before/after records.
An independent auditor recomputed all 84 summaries, order balance, CPU/wall/GC
accounting, semantic hashes, and completion bindings. That audit did not
independently reread the large fixture and library files; their controller
records agree.

## Validation and limits

The exact clean candidate passed 51,538 installed-test assertions in 1,766
blocks, with no failures, errors, or skips and seven existing warnings. Its
required packaged conformance check passed with the existing three warnings
and two notes. The checked source archive matches all 341 packaged source
files from the clean export, with 20 explicit build exclusions. Fifty Rust
tests passed on identical production source. The four new public R regression
blocks passed 34 assertions, covering chunk slices, allocation/collection
stress, embedded-NUL cleanup, cancellation, and successful reads afterward.
The controller's eight rejection tests passed normally and under Python
optimization; 42 untimed qualification cases passed before acceptance.

Main's comparison and grouping changes are separately integrated in clean
build `e5091034`. That build passed 10,509 assertions in 206 focused Arrow,
ownership, comparison, and grouping blocks, with no failures, errors, or skips
and one existing warning. Controller and native-manifest checks also passed.
The [integration binding](results-2026-10-02/validation/integration-binding.json)
and [package delta](results-2026-10-02/validation/integration-package.patch)
record this qualification. All three nullable runtime files remain identical
to the measured build; the complete package differs. Full installed tests and
required conformance retain their original `20a0daa1` attribution.

The recorded conformance archive also passed a stricter inventory recheck
that rejects extra, duplicate, missing, or non-regular source files and removes
inherited Git repository overrides. Its seven synthetic checker tests passed
normally and under Python optimization. This revalidates the captured archive
without rerunning R conformance.

This is one host and one file geometry. Filesystem caching is uncontrolled,
and binding the fixture files reads them before timing. Fresh R processes
provide fresh R string caches, not cold storage. Raw read CPU intervals range
from 3 to 165 ms. Individual observations have millisecond timer resolution;
six-round medians do not create finer measurement precision. Scalar access
often rounds to zero. There are no uncertainty intervals or process-RSS claims.
The fixtures do not establish performance for compressed files, other string
lengths, arbitrary cardinalities, or different chunk layouts.
