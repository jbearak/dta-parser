# R file-reader comparison, 2026-10-01

This report compares `dtatools::read_dta()` and `read_arrow()` before and after
the reader construction changes, with both tibble and dibble outputs. A
separate comparison places those readers beside base R and major package
readers. The [research note](../../docs/research/r-file-reader-performance-2026-10-01.md)
explains the source evidence and the broader reader survey; the
[benchmark README](README.md) gives the commands and complete protocol.

The measurements use a shared desktop, not an isolated benchmark host. An
unrelated R check used roughly one core during the first approximately 135
observations of the default stage. Intermittent Bun processes often used
roughly one to two cores, and other desktop processes also ran. Seven of
eleven snapshots taken before the large stage completed showed competing
Bun or mds activity; the largest sampled combined load was 378% of one core.
An earlier eight-worker R modelling job ended before timing began, and no
further competing R process was observed after the initial check ended. The
[host-load log](results-2026-10-01/host-load.jsonl) contains 51 snapshots from
16:07:22 through 16:36:26 UTC. It samples only part of execution and does not
establish an uninterrupted quiet machine. All
observations remain in the results. Adjacent baseline/candidate pairs reduce
exposure to slow changes in load, but cannot remove interference or make
small differences conclusive. Bootstrap intervals describe the observed
pairs; they do not account for every source of machine-level variation.

## Assessment

The completed 1,728-observation matrix supports retaining these changes for
the measured workloads. Tibble reads improved in wall time across every
synthetic and large control at both thread settings, with paired intervals
below zero. CPU generally fell as well; some automatic-thread large-input
CPU intervals remain inconclusive. Wide synthetic dibbles and selected India
dibble reads improved, while most other dibble differences remain unresolved.
The evidence does not support claiming that every dibble workload is faster.

The full-workflow checks keep the read-return gains in perspective. Ordinary-R
traversal absorbs much of the improvement on compact and mixed inputs.
The resource cost whose full-workflow interval lies above zero is the serial
mixed DTA tibble RSS increase of 0.50%, about 2.50 MB, with a 95% interval of
0.22% to 1.68%. The default stage also records a small read-subinterval CPU
increase and a whole-process wall increase, detailed below. Large controls
show no interval-bounded regression in any recorded metric. These findings
support the requested wall-time/resource tradeoff, with the stated small
memory cost and uncertainty, rather than a claim of zero regressions.

The results apply to warm-filesystem, first-reader-call workloads on this
shared Mac. They do not establish cold-storage behavior or a universal ranking
of readers and formats. The cross-format results show faster complete
ordinary-double workflows in some external readers, along with different
memory, metadata and compression costs.

## Default-stage results

The default stage completed all 864 timed observations and its before/after
provenance checks. The one-thread supplement and large control results are
reported below. Each cell below reports the signed
percentage change from the median paired candidate/baseline ratio, followed
by its existing 95% bootstrap interval. Negative means lower cost. The wall
medians are shown separately; a ratio of medians need not equal the median
paired ratio. No bootstrap was recomputed for this report.

[reader medians](results-2026-10-01/default/summary.csv),

Tibble read-only wall time fell by 29.25% to 72.73% for DTA and 47.73% to
75.60% for Arrow across the four shapes. Their read-call CPU intervals also
lie below zero. Wide tibble peak RSS fell about 14.3%; the other read-only
memory changes were small. Wide dibble reads improved by 8.33% for DTA and
8.97% for Arrow, with lower CPU and about 1% lower RSS. The other dibble
read-wall intervals span zero, some from roughly -17% to +22%; they do not
establish performance equivalence.

### Cross-format reader comparisons

The following tables use candidate dtatools results and the ten external
methods. All values are medians of six observations. Wall and CPU are
milliseconds; peak RSS is decimal MB for the whole corresponding process.
Read and full-workflow columns come from independent processes. Formats
preserve different metadata and use different compression, as detailed below.
No paired intervals or cross-package significance claims are assigned here.

The fast return of a compact table does not make every subsequent operation
fastest. On the compact fixture, qs2's complete traversal took 175.0 ms and
generic Arrow's took 199.5 ms, compared with 567.0 ms for the candidate DTA
tibble and 679.5 ms for its profiled Arrow tibble. Their respective consume
RSS medians were 439.3, 483.6, 259.8 and 279.3 MB. These are different
storage, validation and representation tradeoffs. qs2's compact fixture is
also only 2.46 MB, compared with 96.02 MB DTA and 100.05 MB profiled Arrow.

Explicit lazy vroom lowers read-return time by deferring work. For example,
its numeric read took 114.5 ms, while the complete workflow took 870.5 ms.
Its `altrep = TRUE` setting enables all ten supported ALTREP types; the
package-default flag recorded by the runtime inventory is a different setting.

## Qualification and measurement boundaries

Before timing, each synthetic reader/library/thread combination first
consumes every column. It compares that result and every column name and
value against independently generated ordinary R values. Numeric storage
differences are removed for the value comparison. Parser problems and
unexpected reader warnings abort qualification. dtatools additionally
checks the requested container and complete `datasig()` equality across
libraries, formats, containers and thread settings.

The private read-only controls recompute complete `datasig()` values from
every value and metadata field. They omit the additional R aggregate
traversal and explicitly record `consumption = "omitted_read_only"` with a
null consumption hash. Every synthetic fixture, and every run containing
consume mode, requires full consumption before signature checks. The
read-only private controls provide no read-plus-R-consumption timings.

Every timed observation uses a fresh R process. Package loading, reader
setup, wrapper bytecode compilation and a full garbage collection precede
the timer. The measured call is the first public reader call in that process;
there is no reader warmup. Package namespaces are already loaded. Input
hashing and qualification warm the filesystem cache, so these are not
cold-storage or package-startup measurements.

Read mode measures the public call, retains the result, checks shape and
container, then exits without scanning values. Consume mode starts with
the same read and then traverses every numeric value as an ordinary double,
counting missing values, and every string's byte length. Casting before
numeric aggregation avoids class-specific rounding. It can allocate double
columns from compact storage, so this workflow's memory use does not describe
all compact-aware aggregates. It also does not promise that every ALTREP
backend makes an ordinary R-vector copy.

For each interval, `proc.time()` records wall time and user plus system CPU
over the same operations. CPU time includes worker threads and represents
core time, not just elapsed time on one core. `wait4()` records whole-process
CPU and peak RSS, including package loading, setup and native allocations.
Read and consume peaks come from separate child processes. Their difference
cannot be interpreted as the allocation size of consumption.

Baseline and candidate run next to each other, with order alternating by
pair. Cases rotate and reverse between pairs. No observations are removed
as outliers. Summaries report medians; dtatools comparisons report the median
of candidate/baseline ratios and a 95% paired bootstrap interval from 10,000
resamples with a fixed seed. Lower ratios mean less wall time, CPU or RSS.
If a pair has an unresolved zero clock, the corresponding ratio and interval
are suppressed while its raw measurement remains present. Six or eight
pairs support workload-specific comparisons, not a universal reader ranking.
