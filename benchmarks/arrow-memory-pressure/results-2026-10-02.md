# Arrow collection pressure, 2026-10-02

Holding 65 MiB of unrelated retained numeric data made every small Arrow read
request a full R garbage collection. Requiring new native allocation before
another collection removes that repeated cost. In six balanced rounds,
eight-row reads fall from 11.76–11.79 ms to 0.170 ms of CPU, a 69.2–69.5×
speedup. Controls with no retained data or 63 MiB remain within 0.8% of their
baseline per-call CPU. This measures steady-state small reads after warmup,
not large-file throughput or first-read latency.

The baseline is merged commit `fd72c3448412b477dfb11e0cf4d26425d5c7a428`.
The measured candidate is `ab64f0e4982e0cef0e6b2e1bbda1aa08f11ada74`.
All 72 observations pass full numeric-value, storage, retained-input,
signature, and source-binding checks.

the five-read collection trace, and the same-interval GC CPU measurements.

## Cause and change

The old policy collected whenever live native bytes exceeded 64 MiB. It did
not distinguish unreachable garbage from a large table the caller still
needed. A full collection could release nothing, and the next read would
repeat it.

The policy now also requires more than 32 MiB of native allocation since the
last successful forced collection. New native owners charge this allocation
counter. Clones and R-owned raw backing do not. Successful collection retires
only the allocation counter claimed by that attempt. Allocations from
finalizers remain pending. Failed or interrupted attempts restore their
claim, and nested reads cannot request another collection during an attempt.
No lock or Rust borrow guard spans an R callback.

The 32 MiB budget leaves headroom for the existing repeated-large-read memory
test. That test, eight reads of a 20 MB numeric column, passes unchanged.
The allocation counter measures cumulative new allocation, not live or
reclaimable bytes. The live-byte threshold remains a separate requirement.

## Protocol and limits

The controls retain zero, 63 MiB, or 65 MiB in a compact integer column.
Eight-row ordinary-double and compact-float files contain observed values,
system missing, and extended missing values. Files are uncompressed and
checksummed, and reads use one thread.

Six rounds balance all condition orders and alternate build and storage
order. Every observation uses a fresh R process. Setup includes one warm
read and explicit collection. Timed intervals include public dispatch,
file I/O, verification, allocation, and automatic or forced collection.
Full value checks and signatures are outside timing. Each interval contains
2,000 reads, except baseline 65 MiB intervals contain 200 because of their
collection cost. Actual CPU intervals span 0.331–2.438 seconds; elapsed
intervals span 0.332–2.436 seconds.

These are warm-cache results on one arm64 macOS host with R 4.6.1 and Apple
clang 21.0.0. Local builds, tests, and other benchmarks did not overlap
measurement; desktop activity was not hardware-isolated. Small control
differences have no formal uncertainty interval. Live-byte endpoint checks
are not peak-memory measurements. This study does not establish memory
bounds for arbitrary workloads or compare R with Stata.

## Correctness and provenance

The original reproduction observed five full collections across five tiny
reads. It now observes zero and verifies the returned values and retained
table. The clean candidate passes 51,504 full-suite R assertions with no
failures, errors, or skips and seven existing warnings. All 47 Rust bridge
tests pass, including six allocation-policy tests. Those policy tests cover
reentrant allocation, nested attempts, failure, panic, and saturation in a
local policy instance; they do not inject a real nested R finalizer read.
The required conformance run passes, including source-archive validation
and `R CMD check`, with three warnings and two notes recorded in its log.
Forty-two repository Python checks and four new controller tests pass.

Clean-build receipts bind the full package sources, compiler inputs,
installed code, and native libraries. Before/after records also bind
fixtures and measurement scripts. The only package change after the
measured candidate is the refreshed native-test manifest. Runtime and test
source remain byte-identical. The final conformance run includes that
manifest update.
