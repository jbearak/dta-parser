# Promote in `replace_values()` as Stata's `replace` does

`replace_values()` and `repl()` now widen a target whose declared storage cannot hold a value, taking the same narrowest-exact storage that `mutate()`, `:=`, and the replacement operators take, and report the change in Stata's own words: ``variable `x` was byte now int``. `:=` and `mutate()` keep promoting silently, because they follow dplyr's contract that the right-hand side defines the column and R verbs are expected to be quiet, while `repl()` translates a Stata command that prints this line. An assignment that selects no rows promotes nothing, matching Stata's `(0 real changes made)`. `promote = FALSE` restores the previous behaviour, an error naming the constructor that would fit, for a translated script that should fail loudly rather than widen.

ADR 0021 made `repl()` strict on the stated ground that "a user who wants Stata's guardrails has them." That ground was mistaken: Stata's `replace` has no such guardrail. It widens automatically and announces it, so a line Stata accepts with a message was an error here, which is the opposite of the fidelity `repl()` exists to provide. The behaviour was measured rather than recalled, and `conformance/stata/replace-promotion.do` records the session against Stata 18.0 MP so the claim can be rechecked instead of re-argued. That measurement also corrected a second error repeated in ADR 0021, `stata-storage-defaults`, and `CONTEXT.md`: Stata does not send an overflowing `long` to `float`. It sends it to `double`, and loses no digits on any promotion. Stata widens when the declared type cannot represent a value at all, through range or through integrality, and never widens for precision.

The one remaining divergence is that precision does promote here: a `float` given a value needing binary64 becomes `double` rather than staying `float` and rounding silently, as it does in Stata. Silence about a lost digit is not a behaviour worth reproducing, and the loud alternative is available at creation through `dta_float()`. Fixing the ladder to match Stata also surfaced a genuine bug in `.narrowest_stata_storage()`, which promoted an overflowing `long` to `float` whenever the values in hand happened to be float-exact. `float` carries 24 bits of integer precision against `long`'s 31, so that step narrowed the integers the column could hold, left a column that would silently round the next long-range integer written to it, and contradicted the arithmetic lattice, which already pairs `long` with `float` as `double`. `long` now skips `float`; `byte` and `int` are unaffected, their whole ranges being float-exact.

The alternative considered was leaving `repl()` strict and documenting the divergence, which is what the branch this supersedes originally did. It was rejected because the divergence had no rationale once the Stata behaviour was measured, and because a translated script silently changing meaning is a worse failure than a widened column. Making the report a warning rather than a message was also considered and rejected: promotion is now the intended, Stata-faithful path, and a warning would overstate it and trip `options(warn = 2)` in callers' pipelines.
