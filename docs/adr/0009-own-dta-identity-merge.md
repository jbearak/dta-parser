# Own a DTA merge with Stata missing-code identity

Neither base `merge()` nor dplyr joins can reproduce Stata's key identity for columns read by `read_dta()`. R matching treats system missing `.` and every extended missing `.a` through `.z` as one missing value, so rows that Stata would keep apart match each other, sometimes into an accidental many-to-many expansion. The research note in `docs/r-joins-with-stata-columns.md` also records why the obvious seams fail: base `merge()` sometimes keeps only the left key, so column methods never see right-key metadata, and it owns dataset reconstruction; dplyr's equality proxy doubles as its missingness definition, so encoding the 27 codes as comparable values makes vctrs report them nonmissing and changes unrelated missing-data behavior. That proxy change was prototyped and rejected. The package will therefore own one merge function, `dta_merge()`, that matches keys under Stata missing-code identity while returning the original Stata vectors.

The interface follows Stata's `merge` command rather than base `merge()` or the dplyr join family, but the two data arguments are named `x` and `y` for consistency with base `merge()` and the dplyr joins; `x` plays the role of Stata's master dataset and `y` the using dataset; match results are named `"x"`, `"y"`, and `"match"`, with `"master"` and `"using"` as permanent aliases because they are the vocabulary Stata users bring to the function. The caller supplies `x`, `y`, explicit key names shared by both (`by`), and a required merge relationship: `"1:1"`, `"m:1"`, or `"1:m"`. Data-frame inputs must have unique, nonmissing, nonempty column names because Stata variable identity is name-based and silently collapsing duplicate R names would discard data. Either input may also be a DTA file path, read through `read_dta()` with default arguments, mirroring Stata's `merge ... using filename`; only the merged result then occupies the caller's workspace, and a merge that needs non-default read arguments reads the file first. Many-to-many is rejected; Stata's own manual warns that `m:m` merges are almost always wrong, and a caller who wants a cross of duplicate keys should say so with a different tool. The default result keeps every row, as Stata does. `keep` filters rows by match result and `assert` errors when a disallowed match result occurs, mirroring Stata's options of the same names. The function always generates a `_merge` variable, a `stata_byte` column keeping Stata's 1, 2, and 3 codes under value labels that use the arguments' names, x only (1), y only (2), and matched (3), and errors when either input already has that name. One deliberate divergence: Stata re-sorts the merged dataset by key, while `dta_merge()` returns master rows in master order followed by unmatched using rows in using order. Key order would force the package to define and pay for Stata's sort of 27 missing codes on every merge; callers who need it can sort afterward, and stable input order is the more useful default in R pipelines.

Equality is Stata's: `.` matches only `.`, and each of `.a` through `.z` matches only itself, in every key column, with no option to weaken this. Stata-faithful identity is the reason the function exists; a caller who wants R's missing bucket already has base `merge()` and dplyr. A non-canonical `NaN` payload in a numeric key errors, because it has no Stata identity to match under; the remedy named in the error is `NA_real_` or `tagged_missing()`. An `NA_character_` key also errors because Stata represents a missing string as `""`, and the error names that replacement. The implementation builds an internal tag-preserving proxy per numeric key column, the observed value plus its missing code, and matches on that proxy, so `vec_proxy_equal()` and the package's R-facing missingness contract stay unchanged.

Reconciliation reuses the vctrs policies the package already ships. Key columns coalesce into their common Stata storage type through `vec_ptype2()` and `vec_cast()`, which promote storage losslessly and combine compatible value-label tables with a warning when one code's text conflicts. Every coalesced column, including ordinary character columns, keeps the master's variable label, numbered notes, and characteristics unless each item is absent, then takes the corresponding using metadata. Overlapping non-key variables follow Stata's rule: matched and master-only rows keep the master's values, and using-only rows take the using values, cast through the same common-type policy; there are no suffixed duplicate columns. Stata applies this rule silently; `dta_merge()` instead warns once per merge, naming the overlapping variables, because the using values for matched rows are discarded whether or not they agree with the master and a silent drop is exactly the kind of surprise this package exists to prevent. For the same reason, when the two inputs disagree on a coalesced variable's variable label, value-label table, numbered notes, or characteristics, keys included, an additional warning names those variables; this stays a warning rather than an error so real-world files with drifted metadata can still merge, and an opt-in strict mode can be added if someone needs one. Stata's `update` and `replace` options are out of scope until someone needs them. The dataset label and characteristics come from the master. Dataset notes instead combine in master-then-using source order. The master keeps its note numbers, while using notes are silently renumbered consecutively from one above the master's highest number. If only one input has notes, its representation and numbering remain unchanged. A combined result omits explicit note-number metadata when its numbers are naturally consecutive from one; otherwise it records the numbers. Equal note text remains as separate entries, and a merge errors if the using notes cannot fit below Stata's 9,999 limit. This corrects the original master-only note rule recorded here. The result is a tibble. Byte, int, long, float, and double columns gather source values through one private native batch, taking the master row when present and the using row otherwise. The implementation validates each shared row-index array once, allocates every result through R on the main thread, copies independent columns in Rust worker threads that never call the R API, and attaches the prototype metadata directly to each fresh result. Ordinary columns slice as one data frame per input, and ordinary coalesced columns use one data-frame slice and assignment, so vctrs validates each row plan once instead of once per column. The metadata proxy forwards other compact-vector slices to the native subset kernel, so those callers also avoid a decode and re-encode round trip. Unsupported or named column layouts retain the vctrs fallback.

Issue #120 extended the accepted input classes to base data frames, tibbles, and data.tables while initially retaining an unconditional tibble result. Internal column selection uses class-neutral `[[` extraction rather than one-argument `[`, whose meaning differs for data.table. Issue #106 and ADR 0017 supersede only that return-container decision: `dta_merge()` now follows the resolved `x` input's base data-frame, tibble, or data-table class by default and accepts an explicit output override. It still retains the supplied objects without mutating them or their aliases. Other data-frame subclasses are not part of this compatibility promise.

We rejected masking `base::merge()` with an S3 method because `read_dta()` returns plain tibbles, and giving them a package class to enable dispatch would change the read contract for every consumer. We rejected a join-style verb family because it multiplies the interface while losing the relationship, `keep`, and `assert` model that makes DTA merges checkable. We rejected exporting a surrogate-key helper for use with dplyr because it is shallow: every caller would rebuild the proxy, run the join, and restore key metadata by hand, which is exactly the complexity a package-owned merge hides.
