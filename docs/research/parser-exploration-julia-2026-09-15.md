# Julia parser ownership and execution patterns

Research dated September 15, 2026. This is a design evidence note, with no new benchmark results or implementation. Read it with the [local baseline and constraints](parser-exploration-local-evidence-2026-09-15.md). The architecture reference is locally stored `origin/main` at `b41d8f9d`, not checkout HEAD.

## Scope and source identity

I inspected official documentation and source for Arrow.jl, CSV.jl, Tables.jl, DataFrames.jl, Parquet.jl and Parquet2.jl. The fetched main-branch manifests report Arrow 2.8.1, CSV 0.10.17, Tables 1.14.1 and Parquet 0.8.6. Those are source snapshot identifiers, not proof that every inspected main-branch change belongs to the corresponding release. Stable Arrow documentation was generated January 14, 2026; Parquet2 documentation August 31, 2025; Tables scan documentation August 24, 2026. I did not establish Parquet2's current release number or run Julia. [Arrow manifest](https://raw.githubusercontent.com/apache/arrow-julia/main/Project.toml), [CSV manifest](https://raw.githubusercontent.com/JuliaData/CSV.jl/main/Project.toml), [Tables manifest](https://raw.githubusercontent.com/JuliaData/Tables.jl/main/Project.toml), [Parquet manifest](https://raw.githubusercontent.com/JuliaIO/Parquet.jl/master/Project.toml).

The strongest transferable idea is explicit ownership at the parser-to-table boundary. A second useful distinction is between a batch iterator, a table holding decoded chunks, and a table whose columns have been copied into ordinary mutable arrays. Their construction times measure different work.

## Arrow.jl separates buffer views from mutable columns

Documented behavior: `Arrow.Table(path)` maps the file, reads metadata, and constructs `ArrowVector` views over its buffers. `Arrow.DictEncoded` retains dictionary values plus indices. `Arrow.Table` combines record batches into a table; `Arrow.Stream` yields one table per record batch. Copying an Arrow vector materializes an ordinary Julia vector. Logical type conversion can happen lazily, and `convert=false` retains Arrow-oriented types. Custom field and schema metadata remain separately accessible. [Arrow manual](https://arrow.apache.org/julia/stable/manual/).

The source makes input ownership more concrete: `tobytes(::IO)` calls `read`, `tobytes(::IOStream)` maps the stream, and a supplied byte vector is used directly. `Stream` retains `ArrowBlob` inputs, schema state and dictionaries while producing batch tables. Thus iteration bounds the batch presented to a consumer, but does not prove that a generic input stream is read incrementally from its transport. [Inspected Arrow table source](https://raw.githubusercontent.com/apache/arrow-julia/main/src/table.jl).

The mapping claim needs a qualification. Arrow IPC supports compressed buffers, which must be decompressed to recover the array layout. The format cannot make compressed bytes directly usable as fixed-width values. This is a format-based inference; this pass did not verify Arrow.jl's precise decompression allocator or reader task scheduling. A mapped file also is not an immutable snapshot of a file another process can modify. [Arrow IPC specification](https://arrow.apache.org/docs/format/Columnar.html#compression).

DataFrames.jl documents `DataFrame(table)` with `copycols=nothing`: copy unless the source signals that copying is unnecessary. `Tables.CopiedColumns` supplies that signal. `CSV.read(file, DataFrame)` uses it because the columns were built for that consumer. Arrow tables also avoid copying because their columns are immutable through the documented table interface; `DataFrame(arrow_table, copycols=true)` materializes mutable columns. [DataFrames column ownership](https://dataframes.juliadata.org/stable/lib/types/#The-design-of-handling-of-columns-of-a-DataFrame).

Transfer to dtatools: make buffer ownership explicit inside the existing Arrow adapter. The existing direct dibble completion already addresses output-container construction. The remaining candidate is whether decoded native buffers can become compact representation backing, or be released immediately after filling final destinations. These are different ownership strategies and should be measured separately. Adopting Julia's immutable column behavior wholesale would change dtatools' supported mutation contract.

## Tables.jl makes the boundary small and explicit

`Tables.columns`, `Tables.getcolumn`, `Tables.columnnames` and `Tables.schema` let a consumer work with a column source without depending on its parser. `CopiedColumns` tells the consumer it can assume ownership of already copied columns. Its documentation also identifies an unusually relevant wide-table issue: encoding tens of thousands of names and types in compiler type parameters becomes prohibitive, so `Tables.Schema{nothing,nothing}` can store them as values instead. [Tables consumer interface](https://tables.juliadata.org/stable/using-the-interface/).

Inference for this repository: represent the 5,972-column India plan as runtime descriptors with a small set of storage-specific kernels. Do not generate a unique compiled schema implementation per file unless measurements justify it. Julia's compile latency is not evidence of an equivalent cost in this Rust/R reader. The local namespace-loading fix is already implemented; any remaining fresh-process setup claim needs profiling.

Current stable documentation includes `Tables.Scan`, a declarative request with projection, filtering and row bounds. A source can consume operations it implements exactly and pass the residual request to a generic executor. The order is filter, row bounds, then projection. Merely pruning impossible partitions does not consume the filter. It preserves row count for zero-column results. The documented filter uses SQL-style three-valued missing logic. [Tables scan contract](https://tables.juliadata.org/stable/scan/).

Status caveat: this is a recently generated stable documentation page, not a proposal page. Its source link names commit `b2ed659d186f727cf36286b87344be2f7ca760de`; the linked source could not be fetched in this pass. I did not verify its first released version or compatibility promise. It is useful as an interface example, not a dependency recommendation. Any dtatools scan design must use Stata missing-code identity and its own explicit filter semantics, rather than importing these SQL rules.

## Parquet readers expose work at column and batch boundaries

Parquet2's `Dataset` and `RowGroup` are column-table interfaces over metadata. Loading a selected column leaves other column payloads untouched. The documentation explicitly warns that each `getcolumn` or `load` call rereads and allocates that column; callers should retain materialized columns for repeated operations. `DataFrame(ds; copycols=false)` avoids another column copy. This is a particularly useful warning for a deferred interface: a cheap handle does not imply memoized decoding. [Parquet2 usage](https://expandingman.gitlab.io/Parquet2.jl/).

Parquet2 enables local memory mapping and parallel column loading by default when available. Its per-column controls expose tradeoffs: retained string references keep underlying buffers alive, copying strings changes GC costs, and lazy dictionaries can avoid allocations. Page parallelism is off by default and requires another traversal of the page buffer. Eager page scanning gathers information that enables specialized string and dictionary output; disabling it reduces that scan but can increase output allocation. These are documented tradeoffs, not measured promises for dtatools. [Parquet2 API](https://expandingman.gitlab.io/Parquet2.jl/api/).

Parquet.jl supplies `BatchedColumnsCursor` with a row range, batch row count, optional threading and reusable buffers. Reuse is for consumers that finish with each batch before advancing. The cursor excludes nested schemas. `RecordCursor` separately supports row ranges and column selection. Logical string conversion changes a byte-array representation into Julia strings. [Parquet.jl reader API](https://github.com/JuliaIO/Parquet.jl#batchedcolumnscursor).

Transfer to dtatools: specify whether an output is an owned chunk, a borrowed batch valid until advance, or a final column. Enforce staging budgets in bytes. A row-group or batch count is insufficient on very wide data. Borrowed batches could serve a private eager executor, but exposing them through R requires lifetimes that survive GC and retention by callers.

## CSV.jl provides the row-oriented comparison

CSV.jl splits sufficiently large inputs into concurrent tasks and checks row boundaries. `CSV.Chunks` provides an iterator whose chunks independently infer column types. Its string choices include fixed-width inline values, references into input bytes, and allocated strings. Pooling can use both a uniqueness ratio and an absolute unique-value limit. `PosLenString` views retain input and limit mutation. With manually specified types, invalid values default to missing plus a warning; `strict=true` rejects them. Column selection avoids parsing unselected output columns. [CSV reading documentation](https://csv.juliadata.org/stable/reading.html).

Source inspection shows a row-task phase with task-local columns, followed by a parallel column finalization phase. `ChainedVector` joins task results without requiring one contiguous array. Integer missing sentinels are reconciled across tasks; pooled output constructs references and a shared dictionary. The current source also avoids nested parser task groups when scheduling multiple inputs. [CSV file implementation](https://raw.githubusercontent.com/JuliaData/CSV.jl/main/src/file.jl).

Inference: task-local state followed by column completion is a useful model for mixed-string DTA work. It is not a new numeric row-task proposal: this repository already has numeric row-task and microtile prototypes. A new experiment would need to handle local string dictionaries, merge/remap costs and byte-bounded task outputs. DTA's declared types and fixed row width also avoid CSV's inference and quoted-row boundary problems. CSV's permissive invalid-value policy must not replace semantic read parity.

## Experiments worth carrying to architecture review

These are falsifiable proposals, not performance predictions. Each needs the latest reference implementation as its control, identical files and verification, and the measurement protocol in the local evidence note.

| Experiment | Mechanism and prediction | Stop condition |
| --- | --- | --- |
| Arrow ownership handoff | Classify selected decoded numeric chunks as uniquely owned compatible storage, shared storage, or conversion-required storage. Transfer only compatible owned buffers into compact representation backing. Predict fewer allocated/copied bytes for that class, with unchanged read and mutation semantics. | Stop if the file's layouts rarely qualify, chunk lookup or first mutation erases consumer gains, or ownership cannot be made safe without copying. |
| Arrow decode/fill with byte-bounded staging | Allocate protected final destinations on the R thread, decode a bounded set of selected tasks, fill disjoint ranges, release temporary chunks, then publish. Predict smaller simultaneous decoded-plus-final ownership and lower peak RSS. | Stop if retained dictionary/source dependencies prevent release, synchronization regresses matched elapsed time beyond the agreed tolerance, or interruption/validation requires whole-result retention. |
| Mixed-string task completion | Extend the existing row-task experiment with owned task-local string state and deterministic column completion. Predict less worker idle time on skewed mixed schemas; measure dictionary merge, remap and final R string construction separately. | Stop if merge/remap work, duplicate dictionaries or final R-thread work consumes the parallelism gain. Do not repeat the already explored numeric-only design. |
| Representation-aware string admission | Compare existing dictionaries with a measured decision based on unique count, string lengths and native bytes retained. Predict a lower allocation or hashing cost in high-cardinality columns while preserving ordinary Stata string vectors at publication. | Stop if deciding or switching representation costs more than it saves, or low-cardinality cases regress. Source-backed string views require a separate retention and mutation study. |
| Consumer-complete ownership accounting | Instrument time and live bytes at planning, verification, decode, final-column filling and publication. Include full traversal and first mutation after return. Predict that the proposed ownership change removes an observed allocation/copy stage rather than moving it after the reader clock. | Reject a read-time win when equivalent consumer work or semantic qualification is deferred. |

A public scan API is useful for subset and aggregate workflows, but cannot resolve the full-load Stata comparison by changing the workload. The rejected deferred DTA default should stay rejected unless a new consumer-specific contract and measurements establish a different use case. Julia's best contribution here is precise ownership and completion semantics at narrow internal boundaries.
