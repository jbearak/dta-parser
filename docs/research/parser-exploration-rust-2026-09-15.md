# Rust parser exploration, September 15, 2026

## Findings

The most concrete Rust-inspired opportunity is to change how Arrow buffers become the final dibble. The reader currently retains decoded Arrow chunks, then allocates and fills separate R or native columns. Streaming verified chunks into final storage could reduce their overlapping lifetimes. Retaining owned Arrow chunks in ALTREP is a larger alternative. These are hypotheses about work and memory, not measured speedups.

DTA already has the main mechanisms that make Rust Parquet readers efficient: a schema plan, type-specific column loops, bounded input blocks, and worker ownership of independent output columns. The newer measured implementation also batches compact bytes and adjusts workers for the selected geometry. Recommending those mechanisms as new work would repeat completed work.

This note applies the research and unslop skills. It contains source inspection and proposed experiments only. No implementation or benchmark ran for this exploration.

## What the Rust implementations do

### Separate file structure, decode state and output batches

Arrow-rs separates Parquet row groups and column chunks from output record batches. `ArrowReaderBuilder` accepts projection, row groups, row selection, filters and batch size. Its batch size controls returned batches and allocation hints, rather than redefining the file's page boundaries. Row-group filtering precedes row selection, which precedes row filters. Page indexes improve skipping when present. [Reader builder](https://arrow.apache.org/rust/parquet/arrow/arrow_reader/struct.ArrowReaderBuilder.html).

`ColumnValueDecoder` accepts an uncompressed data page and its encoding, retains dictionary state, writes a requested number of values to an output buffer, and supports skipping values. This interface makes decode progress independent of the consumer's batch size. [Value decoder contract](https://arrow.apache.org/rust/parquet/column/reader/decoder/trait.ColumnValueDecoder.html).

The relevant lesson is to keep three units separate in dtatools: bytes fetched, values converted, and final storage allocated. DTA's 8 MiB input block is an I/O and scratch bound. It need not also be the granularity of every numerical conversion. An Arrow record batch is a file boundary. It need not require retaining all batches before filling the final dibble. This is an architectural inference, not a claim that Parquet's batch size should become dtatools' default.

### Specialize bulk loops instead of dispatching every cell

Arrow-rs chooses decoders by physical type and encoding. Its decoder API writes a caller-supplied output slice. The byte-stream-split decoder specializes widths with const generics and fills typed output bytes directly. Its implementation has ordinary nested loops; the source does not justify claiming that every decode uses explicit SIMD instructions. [Decoder dispatch](https://arrow.apache.org/rust/src/parquet/encodings/decoding.rs.html), [byte-stream-split implementation](https://arrow.apache.org/rust/src/parquet/encodings/decoding/byte_stream_split_decoder.rs.html).

The bit unpacker generates separate functions for compile-time bit widths and dispatches into them, exposing fixed masks and shifts to the compiler. That pattern transfers to DTA as dispatch once per type, endian order and storage contract. The actual bit-packing algorithm does not transfer because DTA cells are stored at fixed byte widths. [Generated unpackers](https://arrow.apache.org/rust/src/parquet/util/bit_pack.rs.html).

Dtatools already validates each strided column range before its type-specific observation loop. The newer reference's compact-byte path calls `try_push_byte_rows` for a whole row span. Its Arrow compact fill still visits values and classifies missing values before writing destination storage. That remaining loop is a candidate for measuring bulk copying plus a specialized missing-value reduction. Any replacement must preserve version-specific Stata sentinels and float NaN behavior. [DTA kernels](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/dta-tools/src/file.rs), [Arrow compact filling](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/rust/src/arrow_ffi.rs#L2341).

### Share plans, select a useful parallel axis

`ArrowReaderMetadata` stores shared metadata and schema in reference-counted owners. It supports loading metadata once and constructing several readers with different selections or on different threads. [Metadata ownership](https://arrow.apache.org/rust/parquet/arrow/arrow_reader/struct.ArrowReaderMetadata.html).

Polars' eager Parquet implementation chooses between row groups and columns using available row groups, projected column count and pool size. It turns column parallelism off for a single selected column. Its public strategies also include a predicate-first mode. These are shape-dependent policies rather than a rule that more threads are always faster. [Eager reader implementation](https://github.com/pola-rs/polars/blob/main/crates/polars-io/src/parquet/read/read_impl.rs), [strategy API](https://docs.pola.rs/api/rust/dev/polars_io/parquet/read/enum.ParallelStrategy.html).

Dtatools already has a two-axis Arrow task queue: each task covers contiguous selected columns within a batch, and workers use private readers. DTA assigns columns by byte-width weight and overlaps coordinator input with worker decoding through bounded channels. The latest DTA reference already adjusts workers for compact selection geometry. The new question is whether an Arrow task's cost should depend on decoded bytes, compression, string length and output conversion rather than column count alone. [Arrow tasks](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/dta-tools/src/arrow/read.rs#L1610), [DTA ownership and input pipeline](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/dta-tools/src/file.rs).

### Zero-copy requires ownership through the consumer

Arrow-rs' zero-copy IPC example maps a file, wraps the mapping in an owned `Bytes`, converts it to `Buffer`, and slices that buffer for `FileDecoder`. The returned arrays retain the underlying owner. This avoids copying uncompressed array data into another Arrow allocation. It says nothing about an R consumer that later copies the array into R storage. [Official example](https://github.com/apache/arrow-rs/blob/main/arrow/examples/zero_copy_ipc.rs).

`FileDecoder` keeps properly aligned buffers. Its default repairs misalignment by allocating and copying; requiring alignment makes misalignment an error. Skipping validation is unsafe and requires valid trusted input. In the local 59.2.0 sources, `Buffer::from(Vec<T>)` already transfers the vector without a second copy. Dtatools' `buffer_from_bytes` therefore is not evidence of an extra vector-to-Arrow copy. [IPC alignment and validation](https://arrow.apache.org/rust/arrow_ipc/reader/struct.FileDecoder.html), [local ownership implementation](/Users/jmb/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/arrow-buffer-59.2.0/src/buffer/immutable.rs:125).

Polars exposes chunk consolidation separately from IPC reading. Consolidation makes columns contiguous by combining chunks. Its memory-mapped IPC mode only works for uncompressed files and requires the data to remain valid for the mapping's lifetime. [Polars IPC reader](https://docs.pola.rs/api/rust/dev/polars_io/ipc/struct.IpcReader.html).

For dtatools, the concrete copy boundary is later. `ArrowReadColumn` owns `Vec<ArrayRef>`, `plan_read_column` allocates destination storage, and `run_column_fills` copies or converts into it. That structure exists in both the checkout and newer reference. The observed peak RSS is consistent with overlapping input and output allocations, but RSS alone does not attribute every byte. [Chunk results](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/dta-tools/src/arrow/read.rs#L89), [destination planning](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/rust/src/arrow_ffi.rs#L2212), [fill execution](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/rust/src/arrow_ffi.rs#L3008).

### Predicate efficiency depends on which rows survive

Arrow-rs' `RowFilter` documentation explicitly warns that early filtering may lose when a predicate needs many columns, retains nearly all rows, or removes scattered rather than contiguous rows. Polars' implementation estimates prefilter cost from the number of transitions in a selection bitmap. Selectivity alone misses that distinction. [Row filter tradeoffs](https://arrow.apache.org/rust/parquet/arrow/arrow_reader/struct.RowFilter.html), [Polars prefilter cost](https://github.com/pola-rs/polars/blob/main/crates/polars-io/src/parquet/read/read_impl.rs).

The transferable idea is a choice among contiguous ranges, sparse gathers and full conversion after a predicate. It cannot improve a full read with no predicate. DTA's row-major storage also means projecting a few columns does not make all other columns' bytes disappear from the observation-block read. An IPC checksum covers the full touched buffer, so selecting a few rows inside it can still require reading and hashing the whole buffer. [DTA observation reads](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/dta-tools/src/file.rs), [verified decode and slicing](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/dta-tools/src/arrow/read.rs#L1530).

### String representations can avoid repeated payload copying

Polars uses 16-byte string views. Strings up to 12 bytes are inline; longer strings refer to owned buffers. Gather and filter operations can copy views while retaining payload buffers. The tradeoffs include larger per-value descriptors and keeping unused payload bytes alive after filtering. [Polars string design](https://pola.rs/posts/polars-string-type/).

Dtatools already uses dictionaries and deferred R string materialization. Replacing those with a view for every row may cost more for low-cardinality survey strings. A view-backed alternative is worth testing for high-cardinality fixed strings and `strL`, especially if the output retains already-owned payload buffers. It is not a reason to change the durable IPC profile to `Utf8View` without a separate format decision. [Existing string and deferred-decoding research](read-dta-construction-and-deferred-decoding.md), [Arrow profile decision](../adr/0010-promise-stability-for-frozen-arrow-profiles.md).

## Experiments worth handing to architecture agents

These proposals are ordered by how directly they address observed work. Every experiment should compare against the latest local reference rather than silently timing the older checkout.

| Experiment | Change under test | Falsifiable prediction and rejection condition |
| --- | --- | --- |
| Bounded Arrow decode-to-final-storage | Allocate output from the prepared schema, decode and verify a bounded group of chunks, fill its final ranges, then release temporary arrays. Preserve worker isolation from R APIs. | Temporary Arrow bytes should stop scaling with the full output size. Reject if measured peak does not fall or repeated full-read time regresses outside run variability. |
| Owned chunk adoption | Let eligible compact ALTREP retain Arrow buffers and chunk offsets, beginning with uncompressed, compatible numeric storage. Copy on mutation and when contiguous storage is required. | Load should allocate fewer destination bytes. Measure load plus full numeric consumption, random access and first mutation. Reject a default-path claim if savings only defer equivalent or greater work. |
| Bulk compact Arrow fill | Replace per-value writes with contiguous chunk copies where the storage matches; scan missing values using a type-specific reduction, or fuse the reduction with a suitable copy loop. | Count copied bytes and missing-classification CPU separately. Reject if an additional memory pass outweighs dispatch savings. Keep all missing sentinel and NaN cases in qualification. |
| Costed Arrow task grouping | Group by estimated decoded bytes and conversion kind, keeping task order deterministic and limiting live decoded output. | Worker idle time or tail latency should fall on mixed narrow numerics and large strings. Reject if equal-count grouping already balances the measured workload or setup dominates. |
| Reuse one prepared read plan | Reuse parsed footer, selected metadata and classification within a single open snapshot through selection and fill. First measure repeated parsing or classification. | Allocation and metadata CPU should fall on zero-row and wide-small cases. Reject if those phases are already shared or the remaining cost is R attribute construction. Do not add a persistent path-only metadata cache. |
| Retained payloads for distinct strings | Compare existing dictionary construction with owned byte views for high-cardinality strings, including subsequent gather and mutation. | Payload allocation/copy volume should fall. ## Constraints the architecture must preserve

The dtatools profile stores Stata missing values, metadata and per-buffer checksums. Frozen profile versions must remain readable. Ordinary projection consumes selected field documents; full summaries, profiled predicates and stored-signature operations can consume the complete schema. These validation scopes are part of behavior, not optional overhead. [Profile contract](../adr/0010-promise-stability-for-frozen-arrow-profiles.md).

The IPC reader already bounds decompression by the declared expected length, checks buffer bounds and array structure, and verifies selected buffer checksums before slicing. A checksum is not a proof of structural validity, and verification still touches bytes under memory mapping. Keep these checks while reducing duplicate allocation or passes. Mapping also creates a lifetime obligation if another process mutates or truncates the file. [Current checks](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/dta-tools/src/arrow/read.rs#L880), [mapping contract](https://docs.pola.rs/api/rust/dev/polars_io/ipc/struct.IpcReader.html).

R allocation, attribute installation, protection and interrupt handling remain coordinator responsibilities. Workers may write disjoint native destinations only under an ownership contract that survives failure and cancellation. The current Arrow adapter already follows that separation; a streaming sink must retain it. [Current fill separation](https://github.com/jbearak/dta-parser/blob/b41d8f9d8dba260b8c93d5c7d83cb12ee8102600/r-package/dtatools/src/rust/src/arrow_ffi.rs#L2007).

Finally, Parquet's selective-query results cannot predict a full DTA read. DTA has neither Parquet column pages nor their statistics, and IPC does not incur Parquet value decoding. The useful contribution from these Rust readers is their ownership, planning and bulk-conversion structure. The next measurement should identify avoidable bytes and passes in this reader before choosing another file format or adding more concurrency.
