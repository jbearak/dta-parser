# Python reader architecture and lessons for dtatools

Research date: 2026-09-15. Scope: PyArrow, Arrow C++, pandas, Polars, and Arrow CSV/IPC. This is source research, with proposed experiments and no new benchmarks or implementation.

## Assessment

The most useful Python precedent is to preserve a reader's column buffers across the boundary into the user's table. Where conversion is necessary, bound how much decoded input remains live while constructing the destination. For `read_arrow()`, that is a more concrete starting point than changing compression or adding workers. For `read_dta()`, inspect the coordinator, useful work per worker, and whole-column conversions before pursuing a lazy default. These are architectural judgments, grounded in the mechanisms and local evidence below.

## How the readers are structured

### Native parsing and table conversion are separate costs

With the PyArrow engine, pandas 3.0.5 calls `pyarrow.parquet.read_table()` and then `arrow_table_to_pandas()`. Its API exposes `dtype_backend="pyarrow"` for an Arrow-backed result and `to_pandas_kwargs` for conversion options. Thus a Python reader comparison needs to name both the file engine and the final column representation. [Pinned pandas implementation](https://github.com/pandas-dev/pandas/blob/v3.0.5/pandas/io/parquet.py), [pandas read API](https://pandas.pydata.org/docs/reference/api/pandas.read_parquet.html).

Arrow's NumPy-backed pandas conversion can share numeric values when the type is compatible, there are no nulls, and the column has one chunk. Multiple chunks require copying into contiguous storage. `split_blocks=True` avoids initial block consolidation; later operations can consolidate anyway. `self_destruct=True` releases Arrow buffers as columns convert, but shared allocations can keep them alive until all referencing columns finish. It invalidates the source table and is not an ownership model to copy literally into R. [Arrow conversion constraints](https://arrow.apache.org/docs/python/pandas.html#memory-usage-and-zero-copy).

Locally, `dtatools_read_arrow_rust()` first obtains an `ArrowReadResult` containing all selected Arrow chunks. It then allocates destination vectors, fills them, and finalizes R columns while retaining that result. Profiled compact numbers receive new compact storage; ordinary doubles receive R vectors. This establishes an interval of source/destination overlap, though it does not by itself explain every byte of the observed peak. [Read orchestration](https://github.com/jbearak/dta-parser/blob/573e636611d5b73afde47f5d5f232c3c4bcc506f/r-package/dtatools/src/rust/src/arrow_ffi.rs#L3298), [destination allocation](https://github.com/jbearak/dta-parser/blob/573e636611d5b73afde47f5d5f232c3c4bcc506f/r-package/dtatools/src/rust/src/arrow_ffi.rs#L2212).

Transferable idea: let the native reader transfer compatible owned buffers, or consume bounded groups of chunks into preallocated destinations and release each group. Which option wins depends on subsequent operations and the cost of supporting chunked ownership. R publication and R API calls still need their existing main-thread boundary.

### Typed batches and ownership transfer precede exotic kernels

Arrow C++'s pinned `TypedColumnReader` reads batches into typed value buffers. Its `RecordReader` separates reservation, reading and release, with `ReleaseValues()` and `ReleaseIsValid()` transferring filled buffers to callers. `ReadBatchWithDictionary()` exposes dictionary indices and values, but the dictionary is reader-owned and callers must preserve it before the reader dies. Batch interfaces can reduce per-value dispatch while keeping ownership explicit. [C++ reader interfaces](https://apache.googlesource.com/arrow/%2B/refs/tags/apache-arrow-20.0.0-rc1/cpp/src/parquet/column_reader.h).

SIMD is an encoding-specific technique, not a property of every Parquet read. Arrow's official 0.17.0 release lists SIMD work for `BYTE_STREAM_SPLIT` decoding. That is evidence of a targeted kernel, not evidence that a particular current binary vectorizes every numeric conversion or that the same kernel applies to DTA row gathering. [Arrow release record](https://arrow.apache.org/release/0.17.0.html).

Locally, compact Arrow filling currently traverses typed chunks value by value, writes each compact value, and counts missing codes. A candidate can use a bulk copy for byte-identical spans and a separate vectorizable missing-code scan, or fuse both in a specialized kernel. It must preserve format-version rules, tagged missings, NaN payloads and temporal handling. The existing measured DTA byte-batch work is an important control, not a new discovery. [Compact fill](https://github.com/jbearak/dta-parser/blob/573e636611d5b73afde47f5d5f232c3c4bcc506f/r-package/dtatools/src/rust/src/arrow_ffi.rs#L2341), [measured batch work](../../benchmarks/reader-refresh/results-2026-09-12-auto/README.md).

### Memory mapping only removes work compatible with the file layout

PyArrow IPC readers can share source buffers when the input supports it, including memory maps and `BufferReader`. IPC files also support random access to record batches. By contrast, Arrow's Parquet guide says encoded and compressed pages still need decoding, so `memory_map=True` does not eliminate the resident decoded arrays. [IPC buffers and access](https://arrow.apache.org/docs/python/ipc.html), [Parquet mapping limits](https://arrow.apache.org/docs/dev/python/parquet/parquet.html#reading-parquet-and-memory-mapping).

The local uncompressed IPC path allocates a byte vector and reads each selected buffer into it before constructing Arrow arrays. Mapping could avoid that allocation/read copy, but the subsequent destination fill remains unless ownership or representation changes too. Existing checksums would also touch mapped bytes before verified return. [Buffer loading](https://github.com/jbearak/dta-parser/blob/573e636611d5b73afde47f5d5f232c3c4bcc506f/r-package/dtatools/src/dta-tools/src/arrow/read.rs#L878), [checksum validation](https://github.com/jbearak/dta-parser/blob/573e636611d5b73afde47f5d5f232c3c4bcc506f/r-package/dtatools/src/dta-tools/src/arrow/read.rs#L1197).

An ordinary file mapping is not an immutable snapshot against concurrent in-place writes. The previous DTA research already distinguishes owned input bytes from a retained path or mapping. Any experiment must state its ownership promise and test unlink, replacement, truncation and mutation behavior. Earlier return alone would not establish equivalent readiness. [Existing ownership analysis](read-dta-construction-and-deferred-decoding.md#deferred-numeric-prototype).

### Projection and filters must reach the reader before materialization

Arrow Dataset scanners push selected columns down to fragments. A filter can exploit partition information or Parquet statistics; otherwise the scanner filters loaded record batches. Its public controls distinguish batch rows, within-file readahead, file readahead and metadata caching. Current documented defaults are 131,072 rows, 16 batches ahead and four files ahead. Increasing readahead consumes memory and may improve I/O utilization. [Scanner contract](https://arrow.apache.org/docs/python/generated/pyarrow.dataset.Scanner.html).

Polars `scan_parquet()` gives its optimizer the file scan, predicate and projection together. Its `prefiltered` strategy first evaluates predicates into a row mask, then reads remaining work across columns and row groups. The docs warn that this strategy is unstable and can lose on unsuitable predicates. Eager `read_parquet().lazy()` cannot recover work already performed. [Polars scan strategies](https://docs.pola.rs/api/python/stable/reference/api/polars.scan_parquet.html), [eager conversion warning](https://docs.pola.rs/api/python/stable/reference/api/polars.read_parquet.html#notes).

Dtatools already projects IPC buffer reads and skips batches outside the requested row window. DTA projection still reads full observation-row blocks while saving selected decoding and allocation. Parquet page/statistics pruning therefore cannot be transplanted into ordinary DTA files. A DTA scan could evaluate predicates first and delay output construction, but without an index it still needs the relevant row bytes. [IPC selection](https://github.com/jbearak/dta-parser/blob/573e636611d5b73afde47f5d5f232c3c4bcc506f/r-package/dtatools/src/dta-tools/src/arrow/read.rs#L1), [DTA projection limits](read-dta-construction-and-deferred-decoding.md#what-the-current-reader-does).

A new lazy query object would be a separate product decision. The previous owned-row numeric prototype was slower than direct eager construction in every full-traversal, signature and known-selection workflow tested. Repeating it without a new cache-sharing or execution argument is weakly motivated. [Deferred results](read-dta-construction-and-deferred-decoding.md#deferred-numeric-timing-results).

### Parallelism includes scheduling and memory budgets

Arrow C++ uses separate CPU and I/O executors so blocking reads do not occupy CPU workers. PyArrow Parquet's `pre_buffer` coalesces requests and issues them through background I/O workers for high-latency filesystems. The docs warn against duplicating filesystem readahead. These mechanisms chiefly address scheduling and storage latency; they are not a reason to increase concurrency indiscriminately on warm local files. [Arrow executors](https://arrow.apache.org/docs/cpp/threading.html), [Parquet prebuffering](https://arrow.apache.org/docs/python/generated/pyarrow.parquet.read_table.html).

Arrow CSV provides a useful counterexample. Full reading can use threads, while incremental `open_csv()` is documented as single-threaded. Block size is in bytes; type inference happens on the first block and then freezes. Bounded memory and multithreading are separate design properties. DTA already has declared storage types, so it does not need CSV-style type inference. [CSV reading controls](https://arrow.apache.org/docs/python/csv.html#incremental-reading), [Stata storage model](../../CONTEXT.md).

The latest local projection sweep found two workers faster than sixteen for India. Its explanation identifies a coordinator reading complete row blocks and waiting for acknowledgements before the next dispatch. That suggests measuring coordinator time, queue wait and bytes processed per worker. It does not yet isolate synchronization, cache contention or heterogeneous core speeds. [Thread sweep and limits](../../benchmarks/reader-refresh/results-2026-09-12-auto/README.md#why-more-workers-slowed-the-projection).

### Strings and validation remain part of the read contract

PyArrow can request dictionary output directly for Parquet `BYTE_ARRAY` fields. Polars exposes contiguous rechunking as a separate step and documents a memory/performance tradeoff for `low_memory`. These designs show that dictionary preservation, contiguous output and bounded memory are deliberate choices. [PyArrow dictionary reads](https://arrow.apache.org/docs/python/generated/pyarrow.parquet.read_table.html), [Polars memory controls](https://docs.pola.rs/api/python/stable/reference/api/polars.scan_parquet.html).

Locally, null-free Arrow UTF-8 columns are scanned and deduplicated into `RStringData`; nullable strings take a main-thread character-vector path. A buffer-backed UTF-8 representation could avoid rebuilding a dictionary for high-cardinality columns. Preserving encoded dictionaries could help when the file already has the required semantics, but ordinary Stata strings and factors must remain distinct. [String filling](https://github.com/jbearak/dta-parser/blob/573e636611d5b73afde47f5d5f232c3c4bcc506f/r-package/dtatools/src/rust/src/arrow_ffi.rs#L2601), [column classification](https://github.com/jbearak/dta-parser/blob/573e636611d5b73afde47f5d5f232c3c4bcc506f/r-package/dtatools/src/rust/src/arrow_ffi.rs#L2041), [domain definitions](../../CONTEXT.md).

PyArrow exposes limits for Thrift metadata allocations and optional page-checksum verification. Those options are separate from projection and decoding. They do not justify weakening dtatools' verified-read contract. The local report found no consistent benefit from disabling verification, and ordinary profiled projection already validates selected field documents rather than parsing every unselected private document. [PyArrow validation options](https://arrow.apache.org/docs/python/generated/pyarrow.parquet.read_table.html), [local verification measurements](../../benchmarks/reader-refresh/results-2026-09-12-auto/README.md#warm-dta-and-arrow-reads), [profile selection contract](https://github.com/jbearak/dta-parser/blob/573e636611d5b73afde47f5d5f232c3c4bcc506f/r-package/dtatools/src/dta-tools/src/arrow/read.rs#L57).

## Falsifiable experiments for the architecture stage

Each experiment should first name its source build. Compare reader return, first useful operation, full traversal and retained/peak memory separately. Preserve dimensions, values, missing codes, names, labels, notes, storage declarations, output container, malformed-input behavior and source lifetime. Compression and checksum settings belong in every result label.

| Experiment | Change to isolate | Evidence that supports it | Evidence that rejects or narrows it |
| --- | --- | --- | --- |
| Consume Arrow chunks incrementally | Fill preallocated destination ranges, then release consumed chunks; bound outstanding decoded bytes | Lower peak RSS and comparable full-read/full-use time with identical output | Peak unchanged because another owner retains chunks, or scheduling cost erases benefit |
| Adopt compatible numeric buffers | Begin with a single uncompressed chunk and exact raw-storage compatibility; retain its owner | Fewer copied bytes, equal signatures and safe replacement/duplication | Common consumers immediately force a larger copy, or compatibility requires value conversion |
| Support chunked owned numeric columns | Retain multiple decoded chunks without compulsory concatenation | Lower allocation and equal complete-workflow time across batch sizes | Frequent cross-chunk operations or materialization make complete workflows slower |
| Specialize compact Arrow fills | Compare existing element loop, copy plus missing scan, and fused typed batch kernel | Reduced conversion phase time with exact missing-code counts | Conversion is a small fraction of total time, or extra scan consumes more bandwidth |
| Extend DTA scheduling beyond the newer adaptive policy | Hold its worker rule constant, then vary queue depth and batch scheduling independently | Less coordinator/worker waiting improves projection and preserves full-read throughput | Existing adaptive scheduling accounts for the available gain or memory traffic dominates |
| Preserve Arrow UTF-8 buffers | Compare current dictionary construction with owned offset/byte storage by cardinality and nullness | Less allocation and faster read plus representative string operations | Repeated values favor dictionaries or R consumers force expensive materialization |
| Add bounded scan execution | Push known projection and a supported predicate before output allocation | Lower complete query time and bytes allocated for selective work | Load-only benefit disappears during evaluation, or validation/ownership behavior changes |

Prefer the first experiment as the least disruptive test of the Arrow memory hypothesis. Buffer adoption and new string storage need deeper integration with dtatools ownership and mutation. A public lazy API should wait for evidence of completed-workflow benefit.
