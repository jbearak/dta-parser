# Benchmark results

Generated by `bench/run.py`; the findings section is written by hand from these numbers.

## Findings

On the 36 public-use NSFG files and the 10 DHS files, ours is faster than
every other reader in its language at reading whole files, at the pass
over every value, at five columns and at a 1,000-row window, taking the
geometric mean over the files (the exceptions on single files are under
"Targets missed"). The other readers' time over ours:

| language | full read (NSFG, DHS) | read + pass (NSFG, DHS) |
|---|---|---|
| R | haven 15×, 41×; readstata13 17×, 46× | haven 7.4×, 15×; readstata13 8.1×, 16× |
| TypeScript | statfmt 15×, 14× | statfmt 8.8×, 9.8× |

These are after plan 0007 (fixes 6 to 9 below), which made ours faster
in both languages; the other readers were not re-run.

The margin is narrowest in R's pass over every value, where dtatools
makes its packed strings into R strings (ADR 0010). Metadata alone is
where the others come closest: readstata13 (which here reads one row)
is as fast or faster on the smaller files, by fractions of a
millisecond.

The project once had Python and Julia packages too, measured in the
same runs. They were removed on 2026-11-09, and their rows, sections,
and reports with them; where a number below was taken through one of
them, the text says so.

### Fixed because of these runs

Each fix is its own commit, with a test where the behaviour can be
tested (1 and 2). Ours was then measured again with `--readers ours`;
the other readers' results were not re-run.

1. **TypeScript, writing** (`js/src/index.ts`). Writing what
   `readColumns` returned meant an array of numbers and `Missing` values
   per column, and a `Uint8Array` per string. A variable may now give its
   `Float64Array` and missing codes, and strings are encoded into one
   buffer. long.dta: 10.2 s and 9.3 GB → 3.5 s and 3.4 GB (statfmt
   18.8 s); 2002_FemPreg: 289 MB → 195 MB (statfmt 187 MB).
2. **Core, chunk size** (`crates/dta/src/reader.rs`). Chunks were 8 MiB
   of rows, but a byte decodes to 9 bytes, so files of byte variables
   held 72 MiB decoded per chunk. Chunks are now 8 MiB decoded. Peak
   memory of a full read of 2015_2017_Male: R 365 MB → 255 MB
   (readstata13 229 MB), TypeScript 573 MB → 418 MB with fix 4 (statfmt
   325 MB).
3. **Core, column room** (`crates/dta/src/reader.rs`). Decoded columns
   grew by doubling; they now reserve a chunk's rows. The native read,
   timed through the Python binding (since removed): 1976_Preg
   7.0 → 4.8 ms, 2015_2017_Male 42.5 → 33.8 ms.
4. **wasm, read buffers** (`crates/dta-ffi/src/wasm.rs`). Appending
   chunks regrew the columns in module memory, which never shrinks; a
   read now reserves its rows.
5. **The harness, not the package**: haven loads tibble and vctrs with
   itself, dtatools on its first read, so 0.08 s fell inside dtatools'
   timed tasks only. Both now load them before the clock.
6. **R, writing packed strings** (plan 0007, `r/dtaparser/src`). The
   writer made every R string of a column `read_dta` had packed (20M on
   long.dta) before writing it; it now writes their bytes. R's write of
   the synthetic files: 9.3× faster (geometric mean), 27% less peak
   memory; long.dta 6.17 s → 0.80 s.
7. **Core, writing by block** (plan 0007, `crates/dta/src/writer.rs`).
   Numbers are filled 1,024 rows per call and rows built column by
   column in 256 KiB slabs, not a dynamic call per cell. The core's
   write of wide.dta, one thread: 5.40 s → 2.02 s. Bytes unchanged
   (`crates/dta/tests/identity.rs`).
8. **Core, reading** (plan 0007, `crates/dta/src/reader.rs`). 2 MiB
   chunks, and numbers decoded into sized columns: the core's read of
   wide.dta 1.00 s → 0.71 s.
9. **Threads** (plan 0007). Large reads and writes (16 MiB and up)
   use up to three threads (half the hardware threads on x86): workers
   read and decode chunks and, in R, fill numeric columns; chunks reach
   the caller in row order. At three threads every read and write
   measured used at most 1.15× the CPU time of one thread
   (`bench/threads/`); e.g. R reads wide.dta 1.19 s → 0.49 s. wasm
   stays on one thread. Geometric-mean speed-ups of R's full read:
   2.2×, 1.2×, 1.9× (synthetic, NSFG, DHS).
10. **TypeScript, strings** (plan 0008 S1–S3). One `TextDecoder.decode`
    per call and a `substring` per value, and dictionaries of repeated
    values built in the wasm module, instead of a `decode` per value.
    Node 24.22, M4 Max, median of 5, string column alone:

    | read | before | after | target |
    |---|---|---|---|
    | groups.dta str17 (300 distinct), `string[]` | 1,635 ms, heap 690 MiB | 520 ms, heap 118 MiB | ≤ 650 ms, ≤ 150 MiB |
    | the same, `strings: "dictionary"` | — | 445 ms, heap 4 MiB | ≤ 450 ms |
    | long.dta str5 + str10 | 1,087 + 1,018 ms | 388 + 419 ms | ≤ 900 ms |
    | long.dta str10 (all distinct, 10M) | 1,018 ms | 419 ms | ≤ 450 ms |

    Node 26 is faster again (groups.dta 446 ms, dictionary 391 ms).
11. **TypeScript, numbers** (plan 0008 W1). Buffers are copied out of
    wasm memory once, not twice, and a budgeted read of numbers no
    longer does work per row: wide.dta's full read 2,195 → 1,706 ms
    (Node 24, best of 2, three alternating runs), against a 15% target.
12. **wasm memory** (plan 0008 M1–M6), Node 24:
    - the strL index costs 20 bytes a strL, not 106–130: reading 10M
      strLs peaks at 773 MiB RSS, not 1,468 MiB, and takes 5.7 s, not
      9.1 s (the index itself is 192 MiB; target 250 MB);
    - running out of module memory is `DTA_TOO_LARGE`, never a trap
      that closes every open file (js/test/memory.test.mjs, against a
      module capped at 64 MiB; before this, each case trapped);
    - a 500 MB text strL reads with RSS +965 MiB (1,909 before; target
      1.1 GiB); a 1 GB binary strL reads (it was `DTA_TOO_LARGE`); a
      600 MB text strL, longer than a JavaScript string can be, is
      `DTA_TOO_LARGE` with RSS +6 MiB (0.x's build crashed making the
      string, at +2.3 GiB);
    - closing the last reader gives the module's memory back. After the
      500 MB strL, RSS stays 490 MiB above where it started: those are
      the decoded string's pages, freed by V8 but not yet taken back by
      macOS (a bare `TextDecoder.decode` of the same bytes leaves the
      same). Before, 1,910 MiB stayed. Target: within 50 MB; missed for
      that reason;
    - previews (`maxStringBytes: 100`) of a 64 MiB strL read under
      1 MB of the file;
    - reading every strL of a 10M-strL file through an adopted index is
      3.3% slower than through the reader's own (target 5%), and skips
      the scan.

On GitHub's x86 runners (2 cores, 4 hardware threads, so two threads)
the CI's thread report shows a full read 1.9× faster at 1.10× the CPU,
but a five-column read 1.4× faster at 1.5× the CPU (0.05 s of work,
mostly copying rows out of the page cache) and a write 1.2× faster at
1.2× (bound by the runner's disk). Those cases are reported, not gated.

### Targets missed, and why

- **R metadata and windows on small files** (by 0.02 to 0.2 ms).
  dtatools builds a tibble with per-column attributes; readstata13's
  "metadata" here is a one-row read without them.
- **R memory** on the pass over every value (7 files) and one full read:
  dtatools keeps the packed text while R makes its strings (ADR 0010),
  and stores every number as a double (ADR 0003) where readstata13 keeps
  R integers.
- **TypeScript memory** reading one 3,000-variable NSFG file
  (2013_2015_Male, 1.6×) and writing three files: ours holds a
  `Float64Array` and a byte of missing code per value (9 bytes), statfmt
  small integers in plain arrays. Writing copies every column into
  module memory before streaming the file, so writing costs more memory
  than reading, and **wide.dta (4.8 GB) cannot be written** from
  TypeScript: wasm32 memory stops at 4 GiB. Writing row blocks as they
  come would lift that; not done here.

### What the correctness checks found

- **Values agree everywhere**: every full read, five-column read, window
  and checksum of every reader equals ours, on every file where both
  ran (missing codes too, where haven keeps `.a`–`.z`).
- **Labels with trailing spaces**: haven and statfmt (both
  ReadStat-based) drop trailing spaces from variable and value labels;
  ours and readstata13 keep the file's text. This is every metadata
  "difference" on NSFG and most on DHS.
- **Writers**: ours writes back values and metadata that the
  open-source readers read as they read the source, in both languages.
  readstata13's writer drops the data label and display formats.
- **Readers that could not finish**: statfmt's write of wide.dta failed
  in the harness, not in statfmt: it wrote the 4.8 GB result with one
  `fs.writeFileSync`, which Node limits to 2 GiB. The harness now
  writes it in pieces; the measurement was not repeated, since the
  other readers' results are not re-run.

The earlier R-only measurements (writing from R, survey-shaped string
columns, grouping) are in [results/r-only.md](results/r-only.md).

## Parquet

Plan 0018's speed and memory gate for R (PR 3): datakit's
`read_parquet()` and `save_parquet()` against arrow 26.0.0, nanoparquet
0.5.2 and duckdb 2.0.0, and pyarrow 26.0.1, polars 2.1.0 and DuckDB
2.0.0 reading our files. Every file and number is in
[results/parquet.md](results/parquet.md), written by
`bench/parquet/run.py`; this section is written by hand from it.

**Every target held in that run**, on the 36 NSFG files, the 10 DHS
files and the three synthetic files, on each of the three inputs
(pyarrow's, polars' and our files of the same data). The run's load
average was 10 to 17, where plan 0018 asks for under 2, and it timed
each library's first call in a fresh process. Measured again on
2026-11-09 at a load of 3, with the calls after the first beside it
("The first call and the calls after it", below), the reads against
arrow are closer than this table says, and one target does not hold:
arrow reads the DHS files whole as fast as we do or faster.

Ours over theirs, geometric means of wall time over the files (NSFG,

### The first call and the calls after it

The table above answers one question: what a fresh R process pays for
its first read. That includes what a library sets up once (arrow
starts sixteen threads; every library's code is paged in), and a busy
machine slows a reader on sixteen threads more than one on two. A
session that reads many files pays the setup once. So the reads were
measured again on 2026-11-09 (after plan 0027), by
`bench/parquet/warm.py`: each case in one fresh process, which makes the
first call and then up to seven more with `gc()` before each; the first
call and the median of the rest are reported. Load average 2.1 to 6.7,
median 3.0. datakit 3.1.0 against arrow 26.0.0 and nanoparquet 0.5.2
(DuckDB's R package was not installed for this run). Every number is in
[results/parquet-r-warm.md](results/parquet-r-warm.md).

Ours over theirs, geometric means of wall time (NSFG, DHS); below 1 is
faster. First call, then warm:

|---|---|---|---|---|---|
| arrow | pyarrow's files | 0.44, 1.03; 0.69, 1.05 | 0.11, 0.15; 0.19, 0.24 | 0.24, 0.31; 0.37, 0.40 | 0.49, 0.51; 0.48, 0.51 |
| arrow | our files | 0.51, 1.28; 0.79, 1.33 | 0.17, 0.25; 0.33, 0.45 | 0.29, 0.41; 0.46, 0.56 | 0.52, 0.53; 0.50, 0.53 |
| nanoparquet | pyarrow's files | 0.52, 0.36; 0.52, 0.39 | 0.33, 0.09; 0.34, 0.12 | 0.26, 0.11; 0.28, 0.15 | 0.84, 0.74; 0.87, 0.90 |
| nanoparquet | our files | 0.61, 0.45; 0.60, 0.47 | 0.54, 0.16; 0.66, 0.24 | 0.33, 0.15; 0.36, 0.20 | 0.90, 0.78; 0.91, 0.94 |

What this changes:

- **Whole files against arrow.** On DHS we are level with arrow on
  pyarrow's files (1.03 to 1.05) and slower on our own (1.28 to 1.33),
  on a quarter to a third of its CPU time (0.23 to 0.31). The earlier
  0.85 to 0.98 came from the busy machine. On NSFG, 0.44 of arrow's
  first call is 0.69 once both are warm. Target 1 (at most 1.05) does
  not hold for arrow's whole-file read of our DHS files.
- **Our files cost us more than pyarrow's copies of them, and arrow
  less.** pyarrow's copies do not carry the dta profile: read from
  them, DHS Tajikistan 2017 wm has no labelled column; from ours, 4,586
  of its 5,160 are labelled, with their value labels. That is the work
  the reader exists for, and arrow does none of it on either file.
- **Five columns and windows** are still well ahead, by less warm than
  on a first call: against arrow, five columns of pyarrow's files are
  0.19 to 0.24 warm, not 0.11 to 0.15.
- **Read and pass** is the same warm as first: about half of arrow's
  time. It depends on the pass. This one sums each column, counts its
  missing values and adds up its text's lengths; arrow's vectors are
  made on first use, and the count of missing values is slow on them.
  A pass that only sums the numbers and takes `nchar()` of the text ran
  faster on arrow's frame of pyarrow's long.dta file than on ours, 3.0 s
  against 3.8 s, in one session on the same day (not part of this run).
- **nanoparquet**, on one thread, is behind in every case, by less on
  read and pass (0.74 to 0.94), where R's own work on the strings is
  most of the time.
- On the three synthetic files, whole-file reads are 0.63 to 0.66 of
  arrow's, first or warm, and long.dta alone is level (111 ms against
  122 ms warm).

Peak memory was not measured again: a process here makes eight reads.
Writes and DuckDB were not rerun.

### Fixed because of these runs

Each is its own commit on the branch.

1. **Snappy, not zstd, by default.** With zstd 3 (the plan's default)
   DuckDB took 1.40 times as long to read our long.dta as its own
   snappy file, 2.38 times on wide.dta, and up to 1.15 times on the
   survey files; pyarrow 1.49 times on wide.dta. Snappy fixed all of
   them. zstd made survey files only 16 to 17% smaller (the size ratio
   is 0.84 on NSFG and 0.83 on DHS: most columns are dictionary-encoded
   before compression) and our reader three times slower on doubles
   that do not compress. zstd writes took 1.03 to 1.29 times as long as
   snappy ones and were still faster than every other library's.
2. **Threads by size.** At first every large read used two threads (see
   below); arrow, on sixteen, read long.dta in 160 ms against our 215.
   Reads now take a thread per 176 MiB of decoded values (up to eight)
   and writes one per 256 MiB (up to six); long.dta then took 148 ms.
3. **R's heap grown once.** A first read in a new session spent a
   quarter to a third of its time in garbage collection while R grew
   its memory a step at a time (13 collections on long.dta). datakit
   now has R make room for the result first: NSFG 1995 read in 0.161 s
   instead of 0.231.
4. **Text copied by the run.** A chunk of plain text, and the PLAIN
   pages of pyarrow's chunks whose dictionary filled, are copied a run
   of values at a time instead of a row at a time.
5. **Column chunks written as they are encoded.** The writer held a
   whole row group's pages (840 MB of wide.dta's) before writing them;
   writing wide.dta with zstd peaked at 6.3 GB, 1.27 times nanoparquet.
   Chunks now go out in order as soon as they are done: 5.0 GB.
6. **A shorter path to a packed column's strings.** nchar() and is.na()
   over groups.dta's 15 million rows took 0.338 and 0.105 s instead of
   0.376 and 0.143; its read and pass had used 0.795 s of CPU against
   0.744 allowed.
7. Earlier, while building: row groups of up to 1 GiB instead of the
   plan's 64 MiB (pyarrow took 2.4 times as long to read a DHS file cut
   into four), and the profile's JSON parsed without copying its
   strings.

### Threads

Plan 0018 sets the Parquet default by plan 0007's rule: each thread
added must make the task faster by at least half of what one thread
does (the speedup gained, per thread added, at least 0.5), and CPU
time must stay within 1.15 times one thread's. Measured in one R
session (`bench/parquet/threads.R`, median of nine runs after one to
warm up, snappy files, load average about 12), the counts that pass
depend on the size of the work: survey files of up to about 250 MiB
decoded stop at two, because much of their work is per column on the
calling thread, while long.dta passes for reads at four and wide.dta at
eight. One fixed count would either hold large reads to two or give
survey files threads that do not pay. So the rule is applied per size,
which plan 0007 left to later stages: reads use a thread per 176 MiB of
decoded values, from two to eight; writes one per 256 MiB of values,
from two to six. Reads and writes under 16 MB use one. These are the
measurements behind them, taken before fixes 3 to 6. Those change a
first read in a new session and the pass after a read, not how a read
scales; fix 5 lets the writer write while it encodes, which can only
help writes on more threads.

### Method

Machine: Apple M4 Max (16 cores: 12 performance, 4 efficiency), 128 GB,
macOS 26.7.1; R 4.6.1; Python 3.13 for pyarrow, polars and DuckDB.
Every case ran five times, each in a fresh process under
`/usr/bin/time -l`, with the file in the page cache; the medians of
wall and CPU time (user plus system) of the task alone, timed inside
the process after its packages loaded, and of the process's peak RSS
are used. Each library used its default thread count (arrow and
DuckDB sixteen, nanoparquet one, ours by the rule above). Writes time
writing the frame `dtaparser::read_dta()` returns, with every string
made first; for DuckDB, labelled columns are plain numbers (it cannot
register the class). The read and pass is the whole read and then one
loop over every value: the sum of the numbers, the count of missing
values and the total length of the text, the same loop for every
library. The plan asks for a quiet machine (load average under 2); this
one carried other work throughout, with a one-minute load average of
9.5 to 17.3 (median 11.9) recorded before each run, so single
measurements are noisier than the plan intended; every comparison ran
under the same load.

## Method

Machine: Apple M4 Max, 128 GB, macOS 26.7.1. R 4.6.1, Node v26.12.1. Ours are this repository's packages as of the commit that adds these results.

| language | reader | version | options |
|---|---|---|---|
| R | dtatools | 1.0.0 | `read_dta()`; strings come back packed, so task 2 pays for making them |
| R | haven | 2.5.5 | `read_dta()`; converts `%td`/`%tc` (no option not to); converted back for checks |
| R | readstata13 | 0.11.0 | `read.dta13(convert.factors = FALSE, convert.dates = FALSE)`; task 5 reads one row (no metadata-only read) |
| TypeScript | @jbearak/dta-parser | 1.0.0 | `openDtaFile().readColumns()`; task 6 gives `writeDtaFile` the columns as read |
| TypeScript | @irbisadm/statfmt | 0.1.1 | `readDta(bytes)` on the whole file in memory; no column selection; task 5 reads one row |

Each file is read once first (page cache warm). Files over 100 MB: a fresh process per run under /usr/bin/time -l, median of five (three over 1 GB). Smaller files: one process per task times a warm-up call, then up to 20 calls (stopping after 60 s once three ran; a warm-up over 60 s is the only run); peak RSS from one more fresh process with one call (a warm-up over 60 s is that run). Every process has 20 minutes. A reader that times out on a file is not run on that family's larger files.

Times are the task alone, from inside the process after its packages loaded (task 6: the write alone, after an untimed read). Peak RSS is the whole process's, from `/usr/bin/time -l`. Node runs with `--max-old-space-size=32768` so that its default heap limit is not what fails. Each task-2 pass is the same loop in every reader of a language (sum of numbers as float64, missing count, string length in characters; JavaScript counts UTF-16 units).

Correctness, outside the timing: each reader's result is hashed per column (numbers as float64 with missing values as a mask, missing codes where the reader keeps `.a`–`.z`, strings as UTF-8), and ours is compared with each open-source reader in its language, on everything both expose; metadata (names, storage types, formats, variable labels, value labels, data label) likewise. Each writer's file is re-read by the language's open-source reader (haven, statfmt) and compared with that reader's read of the source. Task-2 sums agree within 1e-9 × Σ|x|; counts and lengths exactly.
